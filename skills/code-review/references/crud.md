# 维度 4：CRUD 完整性检查

对涉及数据实体（表 / collection / 资源对象）的变更，逐实体核对增删改查四个方向与周边行为是否闭环。

## 4.1 四操作覆盖矩阵

为每个实体画出矩阵，核对缺项是否为有意为之：

| 操作 | 检查点 |
|------|--------|
| Create | 入参校验（类型/必填/长度/枚举/边界）；唯一性冲突处理；默认值与服务器生成字段（id、created_at）；创建后返回完整对象还是只有 id |
| Read | 列表分页（page/size 上限防全量拉取）；排序字段白名单；过滤注入；详情不存在时返回 404 而非 null/500；N+1 查询 |
| Update | 部分更新 vs 全量覆盖语义是否清晰；不可变字段（id、owner、created_at）是否被拒绝修改；并发更新（乐观锁/版本号/最后写入获胜是否可接受）；更新不存在记录的行为 |
| Delete | 软删除 vs 硬删除是否明确且一致；删除前确认与权限校验；关联数据处理（级联删除/置空/禁止删除）；删除后列表/缓存/索引同步失效 |

## 4.2 数据一致性

- [ ] **多写一致性**：一次业务操作涉及多表/多存储（DB + 缓存 + 文件 + 远端 API）时，是否有事务或补偿机制？部分失败会怎样？
- [ ] **约束兜底**：仅靠前端校验而 DB 层无唯一索引/非空约束，等于无校验。
- [ ] **字段口径**：同一字段在创建表单、编辑表单、列表、详情、导出中的展示与格式是否一致？
- [ ] **时间与时区**：created_at/updated_at 由谁写入？时区口径统一（UTC 存储、本地展示）？

## 4.3 状态与流转

- [ ] **状态机**：实体若有状态（订单/任务/审批），状态流转是否穷举？是否存在非法跳转路径（如 已完成 → 待支付）？
- [ ] **终态处理**：到达终态后是否禁止进一步修改？UI 上对应按钮是否禁用？
- [ ] **空态/异常态**：列表为空、加载失败、权限不足三种界面是否分别处理？

## 4.4 API 契约

- [ ] 响应结构一致性：错误格式（code/message）统一；分页元信息（total/hasMore）齐备。
- [ ] 幂等性：创建类接口重复提交（双击/重试/网络重发）是否产生重复记录？有无幂等键或唯一约束兜底。
- [ ] 变更兼容：新增必填字段、删除字段、改字段类型对旧客户端的影响。

## 判定级别参考

- P0：可绕过校验写入脏数据、删除无权限校验、部分失败导致数据不一致。
- P1：缺分页、重复提交产生重复记录、状态非法跳转。
- P2：空态/异常态未处理、字段口径不一致。
