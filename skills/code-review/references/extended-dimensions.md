# 扩展审查维度（维度 50–55）

本文件承载维度 50–55，与 `advanced-dimensions.md`（22–48）同级的第二层扩展清单，覆盖：质量门禁、时间正确性、环境隔离、AI/LLM、移动端、客户端可观测等既有维度未覆盖的议题。编号连续，全部默认实装（部分维度按项目类型触发）。

**后续批次**：《code-review skill 审查方案 v4》中尚未落地的规划维度（密码学实践、审计追踪与不可否认性、资金与交易正确性、多租户隔离、数据质量、运维脚本与 CLI、云成本、业务风控、前端安全深化、Runbook、UGC 内容安全）将**顺延编号 56+** 追加到本文件，既有 1–55 编号不再变动。

**边界原则**：标注「边界」的维度与既有维度重叠——审查时以既有维度为主入口，本维度只补增量检查项，合并执行、去重报告，避免同一问题计两次。

## 质量门禁与工程基础

### 维度 50：测试策略与质量门禁
**边界**：维度 17 审「代码是否可测 + 关键路径有无测试」，本维度审**测试体系与门禁机制**。默认启用。

- [ ] **测试分层结构**：单元 / 集成 / E2E 的数量与比例是否合理？测试金字塔是否倒置（脆弱的 E2E 承担主要保障，单元测试极少）？
- [ ] **覆盖率与趋势**：核心模块是否有覆盖率阈值？覆盖率是**趋势监控**（防止只跑一次就放任下滑）还是仅在 PR 里报个数字？是否存在"为覆盖而覆盖"的空断言（只调函数、不断言结果）稀释覆盖率？
- [ ] **CI 门禁阻断**：测试失败是否**阻断合入**（而非"警告可跳过"）？是否存在跳过测试的后门（`--no-verify`、`continue-on-error`、`skip_tests` 开关、被 `@Ignore`/`skip` 标记的用例）？
- [ ] **Flaky 测试治理**：不稳定用例是否有标记、隔离与修复跟踪？重跑即绿是否被当成"通过"而掩盖真实缺陷？
- [ ] **测试数据管理**：测试数据如何构造与清理？是否依赖共享的可变数据集（用例之间互相污染、执行顺序敏感）？测试是否可并行/可乱序执行？
- [ ] **回归基线**：修复线上缺陷时是否**先补可复现的回归用例**再修？已修缺陷是否留下守护用例，防止二次回归？
- [ ] **环境保真度**：测试环境的依赖版本（DB 版本、时区、语言环境、并发量级）与生产的差异，是否会导致"测试通过、线上失败"？
- [ ] **门禁范围**：除测试外，运行单元检查（lint、类型检查、格式化、构建）是否一并作为阻断门禁（与维度 49 联动）？

### 维度 51：时间与时钟正确性
**边界**：维度 4 审「字段时区口径」，维度 23 审「闰年/跨日业务边界」，维度 41 审「Cron 时区」，本维度审**时钟本身与时间运算**。默认启用（交易/分布式/长驻定时任务项目必启）。

- [ ] **单调时钟 vs 墙钟**：超时（timeout）、耗时统计、限流窗口、心跳间隔、重试退避是否用**单调时钟**（`time.monotonic()` / `performance.now()` / `Stopwatch`）？用墙钟计算间隔时，NTP 回拨会导致超时不触发或出现负数耗时。
- [ ] **时钟同步假设**：依赖时钟一致性的场景（跨机日志排序、租约、分布式锁、JWT 过期判定）是否假设了"时钟同步"？时钟偏差容忍度是多少、如何兜底？
- [ ] **DST 与政策变更**：夏令时跳变、时区规则变更时，定时任务是否会**重复执行或跳过**？纯 UTC 存储 + 展示层转本地是否贯彻？
- [ ] **交易日 / 结算日切分**：交易日切分点（如外汇 17:00 NY 收市）、周末与节假日规则是否**显式编码**（而非依赖自然日）？跨日持仓/跨日统计的归属是否明确？
- [ ] **时间精度与来源**：有无 naive datetime（无时区）与 aware datetime 混用？时间戳单位（秒/毫秒/微秒）是否全链路统一？字符串时间格式是否统一（ISO 8601 带时区）？
- [ ] **时间回退的幂等性**：系统时间被回拨后，幂等键、去重表、锁租约、唯一约束的时间字段是否仍成立（不会重复执行/提前过期）？
- [ ] **定时任务与时间源的耦合**：任务是否依赖"上次执行时间"推算下次（时间跳变时会漂移）？超期未执行任务（如服务停机数小时）的补偿策略是否明确？

## 环境与数据流转

### 维度 52：环境隔离与生产数据流转
**边界**：维度 13 审「配置体系」，维度 15 审「PII 合规」，维度 36 审「发布流程」，本维度审**环境之间的硬隔离**。默认启用。

- [ ] **误连生产防护**：开发/调试代码、本地脚本能否连到生产 DB / 生产账户 / 生产第三方？是否有环境标识校验（例如启动时检测到 prod 凭据 + dev/debug 标志即拒绝启动）？
- [ ] **生产数据下行**：prod 数据进测试/分析环境是否**强制脱敏**？是否存在"整库拷贝到测试"的路径？导出文件是否含真实 PII？
- [ ] **环境标识贯穿**：日志、监控上报、埋点、消息是否带环境标识（防止测试流量污染生产看板与告警，也便于事故时区分来源）？
- [ ] **破坏性操作护栏**：批量删除 / 数据迁移 / 回填脚本在生产环境是否有二次确认、限速、dry-run、影响行数上限、审计留痕？（与维度 45 联动）
- [ ] **测试流量隔离**：测试流量是否可能打到生产端点（尤其含计费/发信/下单的第三方接口）？沙箱端点与生产端点是否物理隔离？
- [ ] **凭据分域**：dev 凭据能否访问 prod 资源？密钥/连接串是否按环境隔离、最小权限、可独立轮换？（与维度 33 联动）
- [ ] **多环境配置漂移**：同一配置项在 dev/staging/prod 的取值差异是否显式登记（而非靠记忆）？环境间实例规格/依赖版本的差异是否记录？

## 场景触发维度

### 维度 53：AI / LLM 集成安全与成本（含 AI 功能时启用）
**边界**：维度 3 审通用注入与暴露面，本维度审 **prompt 与模型调用的特有风险**及成本。

- [ ] **Prompt 注入**：用户可控内容（输入、文件名、网页/文档内容、工具返回）进入 prompt 时，是否有指令与数据的分隔、注入检测、系统提示不可被覆盖的机制？
- [ ] **输出不可信**：模型输出是否被当作**不可信输入**处理（结构化校验 / 白名单 / 裁剪 / 长度上限）？是否直接执行模型给出的命令、SQL、代码、URL？（直接执行 = P0）
- [ ] **工具调用权限**：模型可调用的工具（下单、写库、发信、执行命令、文件删除）是否最小权限？高危工具是否需要人工确认或双人复核？工具参数是否服务端二次校验（不信任模型传参）？
- [ ] **成本与配额**：是否有 token 预算、单次调用上限、并发上限、按用户/租户的额度与熔断？是否有异常调用（循环、超长上下文）的拦截？
- [ ] **超时与降级**：模型超时 / 限流 / 不可用时的降级路径（缓存答案、规则兜底、明确报错）是什么？是否存在**无限重试**放大成本与延迟？
- [ ] **数据外泄**：敏感数据 / PII / 密钥是否进 prompt 或上下文？第三方模型的**数据留存与训练条款**是否评估？日志是否记录了完整 prompt（可能含敏感信息）？
- [ ] **幻觉兜底**：模型给出的事实性/数值性结论（金额、日期、代码、结论）是否有来源校验、规则复核或人工确认环节？
- [ ] **可观测与回归**：prompt 是否版本化（可回滚、可对比）？输出是否采样留存？是否有质量回归评估集（prompt 变更后能验证效果不退化）？
- [ ] **多轮与上下文管理**：上下文窗口超限时的截断/摘要策略是否会丢失关键约束？历史消息是否可被用户注入污染？

### 维度 54：移动端特有（Flutter / iOS / Android 项目启用）
**边界**：维度 3 与 25 审通用鉴权与传输，本维度审**移动端平台特有**的安全与生命周期。

- [ ] **本地存储**：token / 敏感数据是否明文存 `SharedPreferences` / `NSUserDefaults` / 普通文件？（应使用 Keychain / Keystore / EncryptedSharedPreferences）
- [ ] **传输安全**：是否启用证书绑定（pinning）？配置是否允许用户安装的根证书（默认信任用户证书 = MITM 风险）？
- [ ] **完整性**：越狱 / Root 检测、应用签名校验、防篡改与防二次打包策略是否到位（按风险等级取舍）？
- [ ] **深链与外部唤起**：deeplink / universal link / intent 参数是否**校验**（防任意跳转、参数注入、开放重定向）？外部传入数据的处理是否可信？
- [ ] **后台与权限**：后台任务限制（iOS 后台执行窗口、Android 后台限制）是否处理？权限申请时机是否合理、被拒绝后功能是否降级可用（而非崩溃/死路）？
- [ ] **弱网与离线**：断网 / 弱网 / 网络切换时的重试、超时、离线队列与**冲突合并**策略是否明确？
- [ ] **生命周期**：进程被杀后的状态恢复是否可靠？推送到达但进程未启动时的处理？前后台切换时的定时器/连接是否正确暂停恢复？
- [ ] **键盘与安全输入**：敏感输入是否禁用截屏/键盘缓存（`FLAG_SECURE` 类）、是否避免敏感信息进入第三方输入法联想？

### 维度 55：客户端错误上报与用户反馈（有前端 / 客户端的产品启用）
**边界**：维度 9 审**服务端**可观测性（指标/追踪/告警），本维度审**客户端异常捕获、上报与用户反馈闭环**。

- [ ] **崩溃与异常收集**：客户端异常 / 崩溃 / 未捕获 Promise / 白屏是否上报（Sentry 类）？上报是否带版本号、设备型号、操作系统、用户标识（脱敏）？
- [ ] **前后端错误关联**：客户端上报是否携带 request id / trace id，可与**服务端日志串联**定位同一次失败？（与维度 9 联动）
- [ ] **噪声控制**：上报是否采样 / 去重 / 分级（防止上报风暴打爆配额或产生费用）？是否上传 sourcemap / 符号表以还原堆栈？重复异常是否聚合（而非逐条上报）？
- [ ] **用户反馈入口**：是否有反馈通道？是否自动附带诊断上下文（日志包、截图、操作路径、环境信息）？
- [ ] **错误可见性与回归**：新版本发布后能否**按版本对比错误率**（判断是否引入回归）？错误率是否有告警阈值？
- [ ] **隐私与同意**：上报内容是否脱敏（不含 PII/凭据）？是否有上报开关与用户同意（合规要求）？离线场景的异常是否本地缓存、联网后补报？
