# 维度 5：产品缺口审查

从产品视角审视变更：代码实现了"能跑的功能"，但距离"可用的产品"还差什么。此维度不要求代码证据到行号，但必须指向具体文件/界面/流程。

## 5.1 需求闭环

- [ ] **需求对照**：变更声称要解决的问题，是否所有验收点都有对应实现？有无"做了 80%，剩下 20% 是用户的必经之路"？
- [ ] **入口可达**：新功能是否有可达入口（菜单/按钮/路由/命令）？还是只能改代码/调接口触发？
- [ ] **出口完整**：操作完成后用户去哪？有无结果页/下一步引导/返回路径？

## 5.2 用户场景覆盖

- [ ] **首次使用**：新用户/空数据时的引导与空态？功能在零数据下是否可用、可理解？
- [ ] **失败场景**：网络失败、接口报错、权限不足、配额用尽时用户看到什么？是白屏/转圈死等，还是可操作的错误提示？
- [ ] **中断恢复**：长流程（表单填写、上传、多步向导）中断后能否续上？刷新页面丢不丢数据？
- [ ] **并发与多角色**：多人同时操作同一数据时的表现？不同角色/权限看到的界面是否合理？
- [ ] **边界量级**：0 条、1 条、1 万条数据下界面与性能的表现？超长文本、特殊字符、表情符号输入？

## 5.3 一致性与可发现性

- [ ] **与既有功能的冲突**：新功能与旧功能是否有重复/矛盾入口？术语是否与产品其他部分一致？
- [ ] **平台一致性**：同一功能在 web/desktop/mobile 多端的行为差异是否可接受、是否有说明？
- [ ] **可发现性**：关键功能是否藏得太深？是否需要新手提示/文档/帮助入口？

## 5.4 数据与运营缺口

- [ ] **可度量**：关键动作有无埋点/统计，上线后如何知道有没有人用、好不好用？
- [ ] **可运营**：出问题时运营/客服能否自助定位（查询入口、管理后台、日志检索）？
- [ ] **回退预案**：功能出问题时能否快速关闭（feature flag / 配置开关）？

## 输出要求

产品缺口按"场景描述 → 当前实现 → 缺失点 → 建议补法"四段式呈现，并标注严重级别（阻断核心场景 = P1，体验缺失 = P2，锦上添花 = P3）。
