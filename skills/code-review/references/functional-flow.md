# 维度 6：功能链路完整性审查

沿真实调用路径逐跳验证，确认从触发到最终副作用的整条链路无断点。方法：从入口（UI 事件 / API 路由 / 定时任务 / CLI 命令）出发，沿 import/调用向下追到数据落点，反向再从数据变化追到界面/外部系统反馈。

## 6.1 链路追踪检查项

- [ ] **入口接通**：按钮 onClick / 路由注册 / 事件订阅是否真实指向目标处理函数？有无"按钮存在但点了没反应"（未绑定、拼写错误、被 disabled 逻辑永远卡住）？
- [ ] **参数传递**：链路每一跳传递的参数名/类型/结构是否匹配？常见断点：前端字段 camelCase vs 后端 snake_case、id 类型 string vs number、分页参数丢失。
- [ ] **异步衔接**：Promise/回调/事件总线的发出方与接收方是否配对？emit 的事件有没有 listener？await 的函数是否真的返回 Promise？
- [ ] **状态同步**：多份状态（本地 state / store / 服务端 / URL 参数）之间的同步路径是否完整？改了一处另一处会不会变旧？
- [ ] **错误传播**：底层抛错后，链路中每一层是处理、上抛还是吞掉？用户最终能否感知失败？
- [ ] **副作用闭环**：数据变更后，依赖它的缓存、列表页、通知、关联实体是否被刷新/失效？

## 6.2 控制流正确性（高发事故区）

- [ ] **循环/条件作用域**：新增 while/for/if 后，原代码块的缩进/大括号归属是否同步调整？对照 diff 逐行核实控制流实际包裹范围与意图一致（典型事故：循环只包住内层一行，外层逻辑永不执行，造成空转）。
- [ ] **早返回截断**：新增的 return/throw/break/continue 是否截断了后续必要逻辑（清理、提交、状态复位）？
- [ ] **分支完备**：if/else、switch、try/catch 是否覆盖所有分支？else 分支缺失时的默认行为是否符合预期？
- [ ] **开关与守卫**：feature flag、端口占用 guard、环境判断（dev/prod）是否让某些路径永远不可达或永远放行？

## 6.3 跨进程/跨服务链路

- [ ] **协议一致**：IPC 消息名、HTTP 路径+方法、WebSocket 事件名两端是否对齐？重构改名时两端是否同步？
- [ ] **生命周期**：依赖的服务/进程未启动时的检测与提示？（典型问题：readiness precheck 检测的对象仅在目标进程内存活，进程外检测必然假阴性——检测逻辑必须与被检测对象的生命周期匹配。）
- [ ] **超时与重试**：每跳有无超时？重试是否幂等？重试风暴会不会打垮下游？
- [ ] **降级**：下游不可用时链路是整体卡死还是有降级路径？

## 输出要求

对每条核心链路给出：链路图（入口 → 处理 → 落点）、断点位置（文件:行号）、断点后果、修复建议。链路断点一律 ≥P1。
