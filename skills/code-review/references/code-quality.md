# 维度 2：代码质量审查

## 2.1 结构与可读性

- [ ] **函数长度**：单函数 >80 行或嵌套 >4 层，应考虑拆分。
- [ ] **圈复杂度**：过多 if/else 分支是否可用早返回（guard clause）、策略表、状态机简化？
- [ ] **命名**：变量/函数/类名是否表意清晰？布尔用 is/has/can，函数用动词开头；避免 `data`、`temp`、`flag`、`a1` 这类无意义命名。
- [ ] **重复代码**：≥3 处相同逻辑应抽函数；跨文件重复应下沉到公共模块。
- [ ] **死代码**：未被引用的函数、变量、import、注释掉的大段代码、遗留 debug 代码。
- [ ] **魔法数/魔法字符串**：业务常量、阈值、超时、重试次数应提取到配置或常量定义（遵循项目约定：magic numbers 提取到 JSON/配置文件）。
- [ ] **注释质量**：注释解释"为什么"而非复述"做什么"；过期的 TODO/FIXME/HACK 是否有归属与跟进？

## 2.2 语言与框架规范

- [ ] **类型安全**：TypeScript 有无滥用 `any` / `as` 强转 / `@ts-ignore`？Python 关键函数有无类型标注？
- [ ] **异步规范**：await 遗漏、未处理的 Promise rejection、回调地狱、async 函数里同步重 IO 阻塞。
- [ ] **资源释放**：文件句柄、定时器、事件监听、订阅、连接是否在组件卸载/函数退出时清理？
- [ ] **导入规范**：循环依赖、通配符 import、未使用的 import、依赖方向倒置（底层依赖上层）。
- [ ] **依赖清单卫生（manifest 级）**：清单文件（`package.json` / `requirements.txt` / `pyproject.toml` / `go.mod` / `pubspec.yaml`）中声明但代码**从不 import** 的**包级未使用依赖**（区别于 2.1 的源码级未使用 import）；版本范围合理性——禁止 `*` / `latest`，警惕 `^` / `~` 静默跨版本引入行为变更；锁定文件（lock）是否入库以保证可复现构建。完整供应链审计见维度 19（本节只做清单级快查）。
- [ ] **框架最佳实践**：React 的 key/effect 依赖数组、Vue 的响应式陷阱、Flutter 的 build 中副作用、Electron 的主/渲染进程职责划分。

## 2.3 可维护性

- [ ] **单一职责**：一个模块/类是否承担了过多职责？
- [ ] **接口设计**：参数对象 >4 个应考虑封装；返回值结构是否稳定可扩展？
- [ ] **耦合**：业务逻辑是否直接散落在 UI 层 / 路由层 / 脚本入口，无法独立测试？
- [ ] **向后兼容**：公开 API / 配置文件 / 数据结构的变更是否破坏既有调用方？
- [ ] **缩进与语法隐患**：Python 等对缩进敏感的语言，循环/条件包裹范围是否符合意图（典型事故：新增循环只包裹了内层调用，外层逻辑块未同步缩进，导致空转）？务必对照 git diff 逐行核实控制流作用域。

## 判定级别参考

- P1：逻辑错误、资源泄漏、未处理 rejection、循环依赖导致的实际问题。
- P2：超长函数、重复代码、魔法数、弱类型滥用。
- P3：命名、注释、风格类问题。
