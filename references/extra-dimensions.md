# 扩展审查维度（维度 10-21）

## 维度 10：错误处理与边界条件

- [ ] catch 不吞错：空 catch、只打印不处理、捕获后状态不复位。
- [ ] 错误分类：用户错误（4xx 语义）与系统错误（5xx 语义）区分，重试策略只对可恢复错误生效。
- [ ] 边界值：空、null、undefined、0、负数、超长、超大量、并发重复提交。
- [ ] 数值精度：金额用整数分/Decimal，禁止 float 直接算钱；浮点比较用容差。
- [ ] 超时兜底：所有外部调用（网络/子进程/锁等待）必须有超时，无默认超时的库要显式设置。
- [ ] 失败后可恢复：进程崩溃/重启后，进行中的任务是能续跑、安全重入还是产生脏数据？

## 维度 11：性能与资源管理

- [ ] 算法复杂度：嵌套循环处理大数据集（O(n²)）能否改哈希查找（O(1)）；循环内不变量计算应外提。
- [ ] N+1 查询、循环内同步 IO、全量拉取后内存过滤。
- [ ] 大对象：无分页的列表接口、一次读入整个文件、大 JSON 反复序列化。
- [ ] 渲染性能：长列表无虚拟化、effect/render 中重计算、无节流的 scroll/resize/input 监听。
- [ ] 资源泄漏：定时器、订阅、事件监听、句柄、连接池未释放；组件卸载后 setState。
- [ ] 缓存策略：该缓存的没缓存（重复计算/重复请求），缓存的没失效（脏数据）。
- [ ] 启动与空闲开销：常驻进程的空转循环（无 sleep 的 while True、零 IO 高频轮询）= P1。

## 维度 12：并发、幂等与事务

- [ ] 竞态：check-then-act、读改写无锁、共享可变状态跨协程/线程。
- [ ] 锁使用：锁粒度、死锁顺序、锁内做 IO/await、异常路径未释放锁（用 with/finally）。
- [ ] 幂等：重试、双击、消息重投下的重复副作用；唯一约束/幂等键/去重表兜底。
- [ ] 事务边界：多步写操作要么全成要么全败；跨系统写入有补偿/对账。
- [ ] 单例假设：假设"只有一个实例在跑"的代码（本地文件锁、内存队列）在多实例部署下是否成立。

## 维度 13：配置与魔法数

> 关键参数硬编码的专项审计见 `references/hardcoded-parameters.md`（维度 4），本维度聚焦配置体系本身。

- [ ] 魔法数提取：业务阈值、超时、重试次数、端口号、限流参数集中到配置（遵循项目约定：JSON 配置文件），代码内不得散落字面量。
- [ ] 环境分层：dev/test/prod 配置分离；生产敏感配置走环境变量/密钥管理，不入库。
- [ ] 配置校验：启动时校验配置完整性与取值范围，非法配置立即报错而非运行中诡异失败。
- [ ] 默认值安全：缺失配置的默认值必须是安全保守值（如未配置则不开 live 模式）。
- [ ] 变更兼容：配置 schema 变更对旧配置文件向后兼容或有迁移说明。

## 维度 14：API 契约与接口设计

- [ ] 公开接口的命名、参数顺序、返回结构是否符合直觉且与既有接口风格一致？
- [ ] 破坏性变更（删字段、改类型、改语义）是否显式声明并配版本号/迁移路径/deprecation 标记？
- [ ] 错误契约统一：错误码、错误结构、分页元信息跨接口一致。
- [ ] 接口粒度：一个接口做一件事；批量化支持（避免调用方循环打接口）。
- [ ] 废弃接口/参数是否打 deprecated 标记并给出替代与下线时间。
- [ ] 契约即文档：OpenAPI/Protobuf/类型定义与实现同步更新，不生"文档说一套、代码做一套"。

## 维度 15：隐私与数据合规（按需，涉个人数据时默认启用）

- [ ] 数据最小化：只收集/传输/存储业务必需的字段；日志与埋点不夹带 PII。
- [ ] PII 识别与脱敏：手机号、身份证、邮箱、地址在展示/日志/导出中按规则打码。
- [ ] 存储与传输加密：敏感数据落库加密、传输 TLS；密钥管理与轮换。
- [ ] 保留与删除：数据保留周期明确；用户注销/删除请求可级联清除（含备份与第三方同步）。
- [ ] 合规映射：涉及中国大陆用户数据时对照《个人信息保护法》最小必要、告知同意、出境限制要求。

## 维度 16：国际化与无障碍（按需，面向多语言/公众用户时启用）

- [ ] 文案无硬编码：用户可见字符串走 i18n 资源文件，不散落字面量。
- [ ] 格式本地化：日期、数字、货币、时区用 locale 感知 API，不手拼格式串。
- [ ] 布局弹性：文案膨胀（中文→英文/德文变长）不破版；RTL 语言（若支持）。
- [ ] 无障碍：语义化标签、alt 文本、键盘可达、焦点可见、色彩对比度达标（WCAG AA）、不只靠颜色传达状态。

## 维度 17：可测试性（按需）

- [ ] 核心逻辑可脱离 UI/网络/DB 单测（依赖注入、接口抽象）。
- [ ] 关键路径有测试覆盖：正常流、边界、失败路径。
- [ ] 测试质量：断言有效（非恒真）、不依赖执行顺序、不依赖外部服务（用 mock/fake）。
- [ ] 确定性：测试不依赖当前时间/随机数/网络，或已做固定化处理。

## 维度 18：兼容性与迁移（按需）

- [ ] API/数据 schema 变更：旧客户端、旧数据是否兼容；破坏性变更有无版本号与迁移路径。
- [ ] 数据库迁移：migration 可回滚、可重复执行、线上大数据量下不锁表超时。
- [ ] 平台/版本矩阵：目标运行时版本语法兼容（如旧 Node 无 ??）、依赖库版本约束准确。
- [ ] 灰度与回滚：变更能否部分发布、快速回退。

## 维度 19：依赖与供应链（按需）

- [ ] 新增依赖必要性：能否用标准库/既有依赖实现？引入包的维护活跃度、体积、license。
- [ ] 版本锁定：lock 文件更新入库；版本范围不过宽（^x 自动升大版本风险）。
- [ ] 已知漏洞：依赖是否存在已知 CVE（可跑 `npm audit` / `pip-audit`）。
- [ ] 间接污染：构建脚本/postinstall 脚本的副作用。

## 维度 20：文档与注释（按需）

- [ ] 公开 API / CLI / 配置项有使用说明，示例可跑通。
- [ ] README/CHANGELOG 随功能变更同步更新。
- [ ] 复杂算法、非直觉业务规则有"为什么"注释。
- [ ] 注释与代码一致，无过期误导。

## 维度 21：变更集与提交质量

- [ ] diff 聚焦：单次变更只做一件事，无夹带的无关改动（顺手格式化、无关重构应拆出单独提交）。
- [ ] 变更规模：超大变更（>400 行核心逻辑）缺陷发现率骤降，建议拆分并提示用户。
- [ ] 提交信息：commit message 说明"为什么改"而非罗列"改了什么"；关联 issue/需求。
- [ ] 遗留物检查：调试代码、临时注释、本地路径、被注释掉的旧实现、未提交的配置变更。
- [ ] 未提交改动盘点：工作区存在大量未提交改动时（如数百行本地修改），提示先梳理提交计划再审查，避免 HEAD 与本地语义不一致。
